# Arena 토론 결과: Claude 토큰의 팀간 불균형 해소 방안

**일시**: 2026-03-25
**프리셋**: 8인
**라운드**: 2회 (독립 의견 + 반박 1회)

---

## 추천안

**옵션 B: 통합 풀 + 소프트캡 + 가시화 (단계적 실행)**

7명 중 6명이 조건부 이상 찬성했고, 핵심 조건으로 "가시화"와 "소프트캡"이 반복 등장했다. 현재 매주 유휴 토큰이 소멸되는 실손실이 발생 중이며, 실행 복잡도가 낮아 즉시 착수 가능하다. 다만 비판자와 품질 악마가 지적한 "전사 동시 중단 리스크"와 "역선택 문제"를 방어하려면, 단순 통합이 아닌 팀별 소프트캡(기본 40%) + 공용 버퍼(20%) 구조가 필수다. 1주 차에 전환하고, 2주 차부터 사용량 리포트를 돌리며, 4주 차에 데이터 기반으로 캡 비율을 조정하는 것이 가장 현실적이면서도 구조적인 접근이다.

---

## 옵션 비교

### 옵션 A: 수동 재배분 (최소 개입)
- **핵심**: 토큰 소진 팀이 여유 팀에 요청해서 좌석/계정을 임시로 빌리는 방식
- **장점**: 실행 즉시 가능(관리자 개입 최소), 기존 팀별 책임 구조 유지, 되돌리기 비용 제로
- **리스크**: 매번 수동 조율 필요(운영 피로 누적), 요청-승인 지연으로 업무 중단 해소 불완전
- **적합 조건**: 토큰 불균형이 월 1~2회 수준의 저빈도일 때, 또는 조직 내 공식 정책 도입이 어려운 과도기

### 옵션 B: 통합 풀 + 소프트캡 + 가시화 (단계적 실행) ★추천
- **핵심**: 전사 토큰을 하나의 풀로 통합하되, 팀별 소프트캡(40%)과 공용 버퍼(20%)를 설정하고 실시간 사용량을 가시화
- **장점**: 유휴 토큰 즉시 활용(비용 제로 효과), 사용 데이터 축적으로 미래 예산 증액 근거 확보, 80% 임계치 Slack 알림으로 자율 조절 유도
- **리스크**: 분기말 다팀 동시 피크 시 전사 중단 가능성(blast radius 확대), Admin Console의 팀 단위 소프트캡 기능 지원 여부 사전 확인 필요
- **적합 조건**: 현재 상황(주 중반 소진 반복, 전사 총량 여유, 예산 동결) — 가장 직접적으로 부합

### 옵션 C: API 키 하이브리드 전환
- **핵심**: 고빈도 사용 팀(DT1 등)은 API 키 기반으로 전환하여 세밀한 사용량 제어, 나머지 팀은 기존 팀 플랜 유지
- **장점**: 토큰 단위 정밀 제어 가능, 팀별 독립 예산 운영으로 책임 소재 명확, 장기적으로 가장 확장성 높은 구조
- **리스크**: Projects/Artifacts/MCP 등 팀 플랜 고유 기능 상실, 전환 비용(개발·교육) 발생, 현 예산 내 해결 제약에 부딪힐 수 있음
- **적합 조건**: 전사 AI 사용량이 지속 증가하여 팀 플랜 한계가 명확해졌을 때, 중기(3~6개월 후) 검토 대상

|------|---------|---------|------|
| 통합 풀 즉시 전환 | 옹호자, 현실주의자: 유휴 토큰 매주 소멸 중, 실행 반나절 | 비판자: 역선택·기득권 박탈 저항, 되돌리기 비용 높음 | **전환하되** 소프트캡으로 방어막 설치, 롤백 기준선 기록 후 시작 |
| 가드레일 수준 | 현실주의자: 과잉 설계 경계, 80/20 원칙 | 품질 악마, 비판자: 분기말 동시 피크 시 전사 중단 | **소프트캡(40%) + 주후반 예비분(20%)** 최소 안전장치 확보 |

| Admin Console 팀별 제어 가능 여부 | 기술 설계자: 가시화는 가능 | 품질 악마: 하드 리밋 미지원 가능성 | **사전 확인 필수** — 미지원 시 수동 모니터링 + Slack 봇 대안 |
| API 키 전환 타이밍 | 기술 설계자, 비전가: 장기적으로 불가피 | 현실주의자: 지금은 과잉 | **별도 트랙으로 분리** — 옵션 B 실행 데이터가 전환 판단 근거 |

## 합의 사항

1. **현 상태(팀별 격리)가 최악이라는 데 전원 동의** — 유휴 토큰 소멸 + 특정 팀 주기적 업무 중단이라는 이중 손실 구조가 매주 반복
2. **실시간 사용량 가시화는 무조건 필요** — 최소 요건: Slack 알림(80%/90% 임계치) + 주간 팀별 사용량 리포트
3. **소프트캡은 안전장치로 필수** — 팀별 기본 할당(40%) + 공용 버퍼(20%) + 초과분 선착순이 최소 방어선
4. **롤백 기준선 확보 후 시작** — 현재 팀별 사용량 데이터를 기록한 뒤 전환해야 되돌리기 판단 가능
5. **API 키 전환은 별도 중기 트랙** — 현 예산 내 해결 제약 하에서 즉시 실행 가능한 건 옵션 B, 옵션 C는 실데이터 축적 후 검토

## 토론 요약

### Phase 1: 독립 의견

| 역할 | 입장 | 핵심 근거 |
|------|------|-----------|
| 옹호자 | 적극 찬성 | 비용 제로·효과 즉시, 유휴 토큰의 즉각 가치 전환 |
| 비판자 | 조건부 찬성 | 공유지의 비극 구조적 필연, 책임 소재 모호화, 근본 원인 미해결 |
| 유저 대변인 | 조건부 찬성 | 현재 UX가 이미 최악(학습된 무력감), 불투명성이 진짜 리스크 |
| 기술 설계자 | 조건부 찬성 | 좌석 비용 중립 확인 필요, Admin Console 가시화 가능, 3가지 대안 아키텍처 제시 |
| 비전가 | 조건부 찬성 | AI-first 문화의 첫 단추, 사용 데이터가 미래 예산 증액 근거 |
| 품질 악마 | 조건부 찬성 | 전사 동시 중단 시나리오(blast radius 확대), 가드레일 필수 |
| 현실주의자 | 즉시 실행 찬성 | 매주 실손실 발생 중, 실행 복잡도 극히 낮음, 단순 시작 후 정교화 |

### Phase 2: 주요 반박 포인트

- **라운드 1**: "단순하게 바로 시작하자"(현실주의자·옹호자) vs "최소한의 안전장치 없이는 더 큰 문제를 만든다"(비판자·품질 악마)로 양분. 기술 설계자가 rate limit 경합 우려를 해소하고, 유저 대변인이 "알림 1개 > 가이드라인 10페이지"를 제시하면서 **"통합 풀 + 소프트캡 + Slack 알림"**이라는 중간 지대로 수렴.

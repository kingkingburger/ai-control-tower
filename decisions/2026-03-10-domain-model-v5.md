# Arena 토론 결과: 도메인 모델(v5) 구조 평가

**일시**: 2026-03-10
**프리셋**: 8인 (7명 독립 의견 + 1명 종합자)
**라운드**: 2회 (독립 의견 + 반박 시뮬레이션)

---

## 추천안

**옵션 B: 구조 유지 + 선택적 단순화 (Stratified Rollout)**

도메인 복잡도는 실재하며 옹호자와 기술 설계자가 공통으로 인정했다. 핵심 아키텍처를 파기하는 것은 비용 대비 손실이 크고, 현실주의자가 지적한 ROI 문제는 "전면 폐기"가 아니라 "기능 노출 전략"으로 해결 가능하다. StreamControl 순서 검증 레이어 추가, 장애 시나리오 명세, 2단계 UX 진입로를 단기 기술 부채로 처리하면 복잡도의 운영 위험을 대폭 낮출 수 있다.

---

## 옵션 비교

### 옵션 A: 전면 단순화 (Pragmatic Rollback)
- **핵심**: threshold + cooldown + email 알람을 독립 테이블 구조로 구현, StreamControl 고정 enum, JSON 완전 제거
- **장점**:
  - 개발/운영 인지 부하 최소화
  - 팀 규모에 맞는 유지보수성
  - 80% 시나리오를 즉시 커버
- **리스크**:
  - 11개 StreamControl 유연성 상실 → 고급 시나리오마다 코드 배포 필요
  - AI-ready 확장 경로 단절
  - 이미 v5까지 진행된 설계 자산 폐기에 따른 재작업 비용
- **적합 조건**: 팀이 3인 이하이거나, 고객이 "단순 임계값 알람"만 요구하는 MVP 단계

---

### 옵션 B: 구조 유지 + 선택적 단순화 (Stratified Rollout)
- **핵심**: 기존 도메인 모델 골격 유지, "Simple 템플릿 모드 → 고급 커스텀 모드" 2단계 UX, StreamControl 순서 검증 레이어 추가, 장애 시나리오 명세 보강
- **장점**:
  - 운영자 UX: 단순 템플릿으로 80% 시나리오 직접 처리
  - 기술 설계: JSON Aggregate Root 유지하되 JSONB 인덱스 + 마이그레이션 경로 확보
  - AI/CEP 확장 경로 보존
  - 기술 부채를 "숨기지 않고" 명시적 로드맵에 편입
- **리스크**:
  - 2단계 UX 설계에 추가 공수 필요
  - StreamControl 검증 레이어가 완성되기 전까지 운영 위험 잔존
- **적합 조건**: 팀이 5인 이상이며, 고객 중 일부가 고급 시나리오를 사용하거나 향후 AI 자동화 로드맵이 있는 경우

---

### 옵션 C: 마이크로 분기 (Dual-Track Architecture)
- **핵심**: Simple Track (독립 테이블 + 고정 파이프라인)과 Advanced Track (현 v5 그대로)을 코드베이스에서 분리 운영, 고객/시나리오별 트랙 선택
- **장점**:
  - 현실주의자와 옹호자 모두 만족시키는 병렬 해법
  - 단순 고객에게 단순 경험 보장
- **리스크**:
  - 코드베이스 분기 → 유지보수 이중 부담
  - 팀 집중력 분산 (기회비용 문제 악화)
  - Simple Track과 Advanced Track 간 데이터 마이그레이션 시 일관성 손상
- **적합 조건**: 완전히 다른 고객군(소규모 공장 vs. 대규모 스마트 공장)을 동시에 공략해야 하는 SaaS 플랫폼

| 장애 시나리오 명세 | (이견 없음, 공통적으로 미비 인정) | 품질 악마 주도 (좀비 알람, Silent failure, 재구축 불가) | **합의**: 경계 조건 명세가 v5의 최대 공백. 전원 보강 필요에 동의 |
| v5 반복 = 설계 수렴 실패 신호 | 현실주의자 (v5라는 사실 자체가 문제) | 옹호자, 비전가 (반복은 도메인 이해 심화의 결과) | **해석 차이**: v5가 수렴 실패인지 진화인지는 변경 이유 기록(ADR)으로 판별 가능. ADR 부재가 실질 문제 |
| AI-ready 확장성 | 비전가 (authorType: "ai"가 핵심 신호) | 현실주의자 (알람은 보조 기능, 핵심 기능부터) | **타임박스 결론**: AI 확장은 아키텍처 가능성으로 보존하되, 18개월 로드맵 전까지 투자 동결 |

## 합의 사항

1. **핵심 구조의 방향성은 올바르다**: 옹호자, 기술 설계자, 비전가가 모두 인정. AlarmRule Aggregate Root와 런타임 3계층 분리(T1/T2/T3)의 설계 의도 자체에는 근본적 반론이 없다.

2. **StreamControl 순서 자유도는 현재 가장 큰 운영 리스크다**: 비판자, 기술 설계자, 유저 대변인, 품질 악마 4인이 독립적으로 같은 문제를 지목. 검증 레이어 없이 프로덕션 진입은 위험하다는 점에 사실상 전원 동의.

3. **장애 시나리오 결과 명세가 부재한다**: 좀비 알람, Silent failure, 재시작 시 상태 재구축 불확실성은 품질 악마가 체계적으로 정리했고, 다른 에이전트들도 개별적으로 같은 우려를 제기. 이 명세 작성이 v5의 최우선 공백이다.

4. **운영자 UX 진입 장벽이 과도하다**: 유저 대변인의 주장에 현실주의자, 비판자가 동조. 기술 내부 복잡도와 노출 복잡도를 분리해야 한다는 데 암묵적 합의.

5. **Redis HA 전략이 명시적 기술 부채로 관리되어야 한다**: 비판자, 기술 설계자, 품질 악마가 각각 다른 각도에서 같은 취약점을 지목. 현재 구조는 소규모에서 유효하나 스케일아웃 시 재설계 비용이 숨어 있다.

### Phase 1: 독립 의견

| 역할 | 입장 | 핵심 근거 |
|------|------|-----------|
| 옹호자 | 강력 찬성 | 도메인 복잡도를 정확히 반영한 설계. 3계층 런타임 분리와 확장성이 강점 |
| 비판자 | 강력 반대 | JSON full-scan, 11개 오퍼레이터 디버깅 불능, Redis 단일 실패점 |
| 유저 대변인 | 조건부 반대 | 7레이어 인지 부하, ruleLevel/ratedLevel 혼란, 순서 변경 피드백 없음 |
| 기술 설계자 | 조건부 찬성 | 구조 올바름. StreamControl 순서 위임과 Redis 확장이 1순위 기술 부채 |
| 비전가 | 찬성 | authorType: "ai" + DryRun + CEP 확장으로 공정 지능화 플랫폼 진화 가능 |
| 품질 악마 | 반대 | 좀비 알람, Silent failure, 재구축 불가 등 장애 시나리오 결과 미명세 |
| 현실주의자 | 반대 | 팀 규모 초과 복잡도, ROI 불명확, 알람은 보조 기능인데 핵심 기능 정체 |

### Phase 2: 주요 반박 포인트

- **갈등 1 — 복잡도의 원인 귀속 (옹호자 vs. 현실주의자 + 비판자)**:
  옹호자는 "복잡도는 도메인 자체가 요구한다"고 주장하나, 현실주의자는 "v5라는 버전 번호가 설계 수렴 실패의 증거"로 반박. 옹호자 반론: 버전 반복은 도메인 이해 심화의 자연스러운 결과이며, ADR(Architecture Decision Record) 없이 버전 번호만으로 실패를 판단하는 것은 무리. 현실주의자 재반박: ADR이 없다는 사실 자체가 문제고, 설계 의사결정 이력 부재는 유지보수 비용을 현실적으로 높인다.

- **갈등 2 — JSON 컬럼 vs. 독립 테이블 (비판자 vs. 기술 설계자)**:
  비판자는 "threshold > 80인 룰 전체 조회" 시 full-scan으로 운영 불능을 주장. 기술 설계자는 "하위 객체는 Rule 없이 독립 존재 이유 없으므로 JSONB Aggregate가 올바른 선택"이라 반박하며 JSONB 인덱스로 쿼리 문제를 해결 가능하다고 응수. 비판자 재반박: JSONB 인덱스는 단순 equality 쿼리엔 유효하나, 범위 쿼리·복합 조건·JOIN에서 한계가 있으며 PostgreSQL 버전 제약도 존재.

- **갈등 3 — StreamControl 유연성의 가치 (옹호자 + 비전가 vs. 비판자 + 기술 설계자)**:
  옹호자는 "11개 오퍼레이터가 코드 변경 없이 시나리오를 해결"한다고 주장. 비판자는 "11! 조합 중 테스트 완료된 조합이 몇 개냐"고 반박. 비전가는 "유연성이 룰 마켓플레이스로 확장되는 근거"라고 옹호자 측을 지지. 기술 설계자는 양쪽 모두를 절충하여 "유연성은 맞지만 유효 조합 화이트리스트 없이는 운영 지식을 설정에 외부화하는 함정"이라고 정리.

- **갈등 4 — 장애 시나리오 명세 책임 (품질 악마 vs. 옹호자)**:
  품질 악마가 "좀비 알람, Silent failure, streamControlState 재구축 불가"를 구체적으로 제시하자, 옹호자는 "Recovery/Escalation 비대칭은 설계 의도이며 신규 알람 우선 정책이 합리적"이라 방어 가능. 그러나 품질 악마 반박: 의도된 정책이라면 문서화가 있어야 하고, 장기 Active 알람이 영구 방치될 수 있다는 점은 운영 현장에서 실제 장애로 이어지는 명확한 결함이다. 옹호자는 이 지점에서 방어력이 약하다.

- **갈등 5 — 개발 우선순위 (현실주의자 vs. 비전가)**:
  현실주의자가 "알람은 보조 기능이며 핵심 기능이 정체된다"고 지적하자, 비전가는 "알람 플랫폼이 AI-ready 구조를 갖추는 것이 OCTOPUS Data Hub의 차별화 핵심"이라 반박. 현실주의자 재반박: AI-ready 확장은 3~5년 후 이야기이고, 지금 팀의 기회비용이 실재하는 손실이다. 비전가 약점: 로드맵 타임라인과 팀 리소스 근거가 없으면 주장이 비전으로만 남는다.

## 다음 단계

1. **[즉시, 2주 이내] StreamControl 유효 조합 화이트리스트 작성 및 순서 검증 레이어 설계**: 11개 오퍼레이터의 의존성 그래프를 작성하고, 허용 조합을 유한 집합으로 정의. 잘못된 순서 입력 시 저장 단계에서 에러 반환. 이것이 현재 전원 동의한 최우선 기술 부채다.

2. **[즉시, 2주 이내] 장애 시나리오 결과 명세 문서 작성**: 품질 악마가 제시한 3가지 시나리오(좀비 알람, Silent failure, 재구축 불가)를 시작점으로, 각 시나리오의 "의도된 동작" vs. "실제 동작" vs. "운영자 관측 가능 여부"를 표로 정리. 이 문서가 없으면 테스트도 SLA도 작성 불가.

3. **[단기, 4주 이내] 2단계 UX 진입로 설계**: "Simple 템플릿 모드(threshold + cooldown + 알림 채널)"를 기본 진입점으로 구현. 고급 모드는 명시적 opt-in. 내부 도메인 모델은 그대로 두되, UI 레이어에서 복잡도를 흡수. 유저 대변인과 현실주의자의 핵심 불만을 구조 변경 없이 해소할 수 있다.

4. **[단기, 4주 이내] ADR(Architecture Decision Record) 소급 작성**: v1~v5 변경 이유를 1페이지 이내로 각각 정리. "왜 JSON 컬럼인가", "왜 3계층인가", "왜 11개 오퍼레이터인가"에 대한 의사결정 근거가 없으면 신규 합류 개발자가 똑같은 논쟁을 반복한다. 현실주의자의 v5 비판을 구조적으로 무력화하는 방법이기도 하다.

5. **[중기, 8주 이내] Redis HA 전략 결정 및 GroupKey 스케일아웃 설계 검토**: Redis Sentinel 또는 Cluster 전환 시 GroupKey 해싱 재설계 범위를 지금 파악. 실제 전환은 나중이더라도, 설계 변경 비용 추정이 완료되어야 현실주의자의 "과설계" 비판에 데이터로 반박 가능하다.

6. **[중기, 8주 이내] JSONB 인덱스 + 대용량 성능 벤치마크 실행**: 룰 1,000 / 5,000 / 10,000개 기준으로 threshold 범위 쿼리 응답 시간 측정. 비판자의 "운영 불능" 주장이 실제 임계점인지, 아니면 JSONB 인덱스로 수용 가능한 수준인지 데이터로 확인. 결과에 따라 옵션 A(독립 테이블)로의 부분 전환 여부를 결정.

# [AI Native Camp 2기] Day 3 — 잘 아는 것과 잘 전달하는 것은 20배 다르다 | Clarify + GitHub

## 요약

AI Native Camp 2기 Day 3 세션(2026.03.04, 온라인)으로 총 2시간 26분 분량의 강의다. 핵심 명제는 **'잘 아는 것(암묵지)과 잘 전달하는 것(명시지)은 20배 차이가 난다'**는 것이다. 원주가 Git/GitHub 개념을 비개발자 관점에서 설명하고, 정구봉이 Claude Code에서 AI에게 의도를 정확히 전달하기 위한 Clarify 스킬과 AskUserQuestion 도구를 심층 소개한다. 패널 세션에서는 송희의 네이버 부동산 스크래핑 프로젝트를 통해 Playwright MCP와 Claude 내장 Chrome의 차이를 라이브 데모로 시연한다. 마지막으로 Slack MCP를 활용해 30개 비공개 저장소를 자동 생성하는 GitHub 자동화를 라이브로 보여준다.

**주요 포인트 3개:**
1. Clarify는 Planning 이전 단계 — 내 의도를 추출하는 프로세스이며, AskUserQuestion으로 가설 기반 다지선다를 제시해 사용자가 놓치고 있는 요구사항을 끌어낸다
2. Playwright MCP와 Claude 내장 Chrome(Clauding Chrome)은 보완 관계 — 로그인 세션 유지는 Clauding Chrome, 탐지 우회는 Playwright가 강점
3. 비개발자도 Git을 써야 한다 — Claude Code 작업 이력 보존, 스킬/프롬프트 버전 관리, 팀 협업의 기반

## 인사이트

### 핵심 아이디어

- **암묵지 → 명시지 전환이 AI Native의 본질** — 맥킨지 보고서 인용: 전문가가 코드 작업 시 60%(38분)를 '이해'에 소비. 잘 안다고 잘 전달되는 것이 아니며, 한국 문화의 고맥락 커뮤니케이션은 AI 활용 시 오히려 비용이 된다
- **Clarify = Planning 이전의 의도 추출 프로세스** — "로그인 기능 만들어 줘"를 Plan 모드로 돌려도 '내가 원하는' 로그인이 아닌 '그냥 동작하는' 로그인이 나올 뿐. 의도를 먼저 캐치해야 한다
- **Unknown Unknowns가 Clarify의 진짜 가치** — Johari Window 4분면에서 '모르는 줄도 모르는 것'을 3분면(Known-Unknown)으로 끌어올리는 것이 핵심
- **토큰은 투자다** — Clarify/Planning 단계에 Opus(고성능) 모델, 구현 단계에 소형 모델 배분. 앞에서 아끼면 뒤에서 열 배로 낸다
- **포맷 변환 자체가 메시지를 바꾼다** — MD → PDF → HTML → React → Remotion 영상 체인은 단순 변환이 아니라 메타미디엄 실험. 동일 내용도 형식에 따라 전달력이 달라진다

### 적용 가능한 점

- **Clarify 4단계 프로토콜**: capture(현재 요청 포착) → AskUserQuestion(가설 기반 질문 설계) → select options(선택) → before/after 비교
- **Sub-agent vs Team-mate 모드 구분**: Clarify는 Team-mate 모드(사용자에게 직접 질문), 구현 에이전트는 Sub-agent 모드(상위 에이전트에 보고)
- **브라우저 자동화 도구 선택 기준**: 인증 필요 사이트 → Clauding Chrome, 탐지 우회 필요 → Playwright MCP, 개발 테스트 → Chrome DevTools MCP
- **비개발자 Git 활용**: commit = '되돌릴 수 있는 저장점', branch = '사본에서 작업', PR = '검토 요청'. Claude Code 작업 이력 관리에 필수
- **개인 비공개 레포지토리로 작업물 관리**: PRD + 실제 프로젝트 파일을 올려서 피드백 루프 구축

### 3. Git/GitHub 개념 설명 (비개발자용) [00:19:00 - 00:31:43]
**원주**

Git과 GitHub의 핵심 개념을 비개발자 언어로 설명.

| 개념 | 비개발자 설명 |
|------|-------------|
| **Git** | 버전 확인, 변경 이유 추적, 협업 실수 복구를 위한 규칙 체계 |
| **commit** | '이 시점의 스냅샷을 나중에 되돌릴 수 있는 저장점' |
| **branch** | 원본을 건드리지 않고 사본에서 작업하는 것 |
| **merge** | 사본 작업을 원본에 합치기 |
| **PR (Pull Request)** | 합치기 전에 다른 사람에게 검토를 요청하는 것 |
| **repository** | 프로젝트 폴더 (파일 + 전체 변경 이력) |
| **PRD** | Product Requirements Document — AI와의 공통 언어 |

- "최종, 최최종" 문제를 해결한 시스템이 Git
- 리누스 토르발즈가 리눅스 오픈소스 협업을 위해 설계
- 컨텍스트 엔지니어링(오늘) → 컴파운드 엔지니어링(내일, 에이전틱 워크플로우) 예고

### 4. Clarify 스킬 소개 [00:31:43 - 01:01:13]
**정구봉**

구봉이 직접 만든 Clarify 스킬의 철학과 설계를 심층 설명.

- **Clarify ≠ Planning**: Planning은 "어떻게 만들지" 계획, Clarify는 "내가 뭘 원하는지" 의도 추출. Planning 이전 단계
- **Garbage In, Garbage Out**: 모호한 입력 → 모호한 결과. "로고 만들어 줘"만으로는 원하는 결과 불가
- **AskUserQuestion 도구**: Claude가 먼저 가설을 세우고 다지선다 선택지를 제시. 사용자가 질문을 설계할 필요 없음
- **Clarify 4단계**: capture(현재 요청 포착) → AskUserQuestion(질문 설계) → select options(선택) → before/after 비교
- **페이즈 분리가 핵심**: 그냥 "모호함을 해소해"가 아니라, 코드베이스나 연결된 툴을 먼저 읽게 한 뒤 맥락 기반으로 질문하게 해야 함
- **Sub-agent vs Team-mate 모드**: Clarify는 Team-mate 모드(사용자에게 직접 질문 가능), 구현 에이전트는 Sub-agent 모드(상위에 보고만)
- Superpowers 플러그인의 brainstorming 스킬도 유사 역할 — 모호한 상황에서 자동 발동

### 6. 패널 세션 — 송희의 네이버 부동산 스크래핑 프로젝트 [01:10:08 - 01:44:22]
**구봉, 송희 (Line Plus 이커머스 팀)**

송희가 부동산 매물 비교 분석 자동화 프로젝트를 발표하고, 구봉이 라이브로 피드백.

- **Phase 1**: 국토부 오픈 API로 과거 거래 데이터 수집 → Google Sheets 자동 연결. 거래량 기준 아파트 5개 샘플 추출. 지역+아파트명 복합키로 고유 식별값 설계
- **Phase 2**: 네이버 부동산 실시간 호가 데이터 Playwright 스크래핑. 호가는 API 미제공 → 스크래핑 필수
- **Clauding Chrome vs Playwright MCP 라이브 데모**:
  - Clauding Chrome: 사용자 로그인 세션 유지 → 인증 필요 사이트에 강점. 설정: `/config` → Chrome enable by default → true
  - Playwright MCP: 깨끗한 Chromium 인스턴스 생성 → 봇 탐지 우회에 강점
  - 네이버가 Claude 직접 접근을 차단 → Playwright로 우회 성공. "신기하게 Playwright는 일반 Chrome처럼 인식되는 것 같았어요"
- **실전 팁**: 데이터 수집은 로컬 CSV 먼저, 마지막에 Google Sheets 업로드가 권장 워크플로우

### 7. 퀴즈 및 Block 3 — Clarify 고급 활용 [01:44:22 - 01:54:02]
**구봉**

퀴즈 섹션(정답 모두 1번). Block 2는 시간 관계로 생략.

- **Unknown Unknowns**: Johari Window 4분면 — 모르는 줄도 모르는 것을 Clarify로 끌어내기. 사용자가 생각도 못 했던 요구사항을 Claude가 질문으로 발굴
- **모델 선택 전략**: Clarify와 Planning 단계에 Opus, 구현 단계에 소형 모델 배분 — 토큰을 전략적 투자로 바라보는 관점
- **포맷 변환 체인**: MD → PDF → HTML → React → Remotion 영상 — 형식 자체가 메시지를 바꾸는 메타미디엄 실험

### 8. GitHub 라이브 데모 — 자동 저장소 생성 및 PR [01:54:02 - 02:26:23]
**구봉, 참가자 '개'**

Slack MCP + GitHub API를 활용한 대규모 자동화 시연 및 참가자 PR 실습.

- **자동화 시연**: Slack MCP로 공지 채널 스레드에서 GitHub 사용자명 파싱 → AI Native Camp 조직에 30개 비공개 레포지토리 자동 생성 → 각 사용자를 collaborator로 초대
- **개인 레포지토리 활용 방식**: PRD(프로젝트 메타 정보) + 실제 작업 파일을 올려서 운영진이 피드백 제공
- **Camp 1기 대비 개선**: 1기는 공용 레포지토리 → 프라이빗한 정보 공유 불가, 비개발자 Git 충돌 문제. 2기는 개인 비공개 레포지토리로 전환
- **참가자 '개' PR 데모**: PRD를 branch로 push → PR 생성 → merge 실습
- 비개발자가 Git을 써야 하는 이유: Claude Code 작업 세션 이력 보존, 스킬/프롬프트 파일 버전 관리

## 도구 및 스킬 언급

- **Clarify** (Claude Code 스킬, 구봉 제작) — Planning 이전의 의도 추출 프로세스
- **AskUserQuestion** (Claude Code 내장 도구) — 가설 기반 다지선다 질문
- **Playwright MCP** — 브라우저 자동화, 봇 탐지 우회에 강점
- **Claude 내장 Chrome (Clauding Chrome)** — 로그인 세션 유지, 인증 필요 사이트에 강점
- **Chrome DevTools MCP** — 브라우저 디버깅/탐색
- **Slack MCP** — 채널/스레드 데이터 접근
- **GitHub MCP / GitHub API** — 레포지토리 자동 생성, 초대
- **Obsidian MCP** — 노트 연동
- **Stitch** (Google 디자인 도구) — AI 대화 기반 앱/웹 디자인 자동 생성
- **Remotion** (React 기반 영상 제작 도구)
- **Vague / Unknown** (Clarify 하위 스킬)

## 개념 정리

| 개념 | 설명 |
|------|------|
| **암묵지 → 명시지** | 전문가의 머릿속 지식(암묵지)을 AI가 처리할 수 있는 형태(명시지)로 변환. AI Native 워크플로우의 핵심 과제 |
| **Johari Window (4분면)** | Known-Known(아는 줄 아는 것), Known-Unknown(모르는 줄 아는 것), Unknown-Known(아는 줄 모르는 것), Unknown-Unknown(모르는 줄 모르는 것). Clarify는 4분면을 3분면으로 끌어올린다 |
| **PRD** | Product Requirements Document. AI와 인간 사이의 공통 언어. 무엇을, 왜, 어떻게 검증할지를 문서화 |
| **Sub-agent vs Team-mate** | Sub-agent: 상위 에이전트의 지시를 받아 실행, 인간에게 직접 질문 불가. Team-mate: 인간과 동등한 협력자로 직접 질문 가능 |
| **메타미디엄** | Alan Kay 개념. 컴퓨터는 모든 미디어를 시뮬레이션할 수 있는 미디어. 동일 내용도 형식 변환 시 전달력이 달라진다 |

# TIL: 대용량 마크다운 문서를 Claude Code로 변환할 때의 토큰 한계와 우회 전략

## 1. Technical Learnings

### Claude Code의 출력 토큰 한계 (32K)

- **핵심 제약**: Claude Code 에이전트의 단일 응답은 약 32K output tokens으로 제한된다. 84K 토큰(도메인 모델)이나 68K 토큰(검증 문서) 크기의 파일을 한 번의 Write로 생성하는 것은 물리적으로 불가능하다.
- **증상**: 에이전트가 파일 내용을 생성하다 중간에 잘리거나, 도구 호출 자체가 실패한다. 에러 메시지가 명시적이지 않아 처음에는 원인 파악이 어렵다.
- **경험 법칙**: 출력 파일이 2000줄(약 40K tokens) 이상이면 단일 Write로는 불가능하다고 가정하고 분할 전략을 세워야 한다.

### 입력 토큰 vs 출력 토큰의 비대칭

- Read로 대용량 파일을 **읽는 것**(입력)은 가능하지만, 그것을 변환하여 **쓰는 것**(출력)은 32K 한도에 걸린다. 읽기와 쓰기의 토큰 한도가 다르다는 점을 항상 인식해야 한다.
- 변환 작업(원본 읽기 -> 가공 -> 결과 쓰기)에서 병목은 항상 출력 쪽이다.

### Python 헬퍼 스크립트를 통한 부분 쓰기(Chunked Write)

- **성공 패턴**: 검증 파일(68K tokens)은 Python 스크립트를 생성하여 파일에 부분적으로 append하는 방식으로 성공했다. 에이전트가 직접 전체 내용을 Write하지 않고, 스크립트가 여러 번에 걸쳐 파일을 조립하게 한 것.
- **비용**: 44 tool uses, 109K tokens 소모. 단순 Write 대비 매우 비효율적이지만, 결과물의 품질은 보장된다.
- **구조**: 에이전트가 섹션별로 Python 스크립트를 생성 -> 스크립트가 `open('a')` 모드로 파일에 append -> 최종 파일 완성.

## 2. Workflow Patterns (잘 된 것)

### Clarify-first 패턴

- 작업 시작 전 clarify 스킬로 요구사항을 명확화한 것이 효과적이었다. 확인한 사항:
  - 대상 독자: 누가 읽을 문서인가?
  - 개선 방향: "가독성 개선"의 구체적 의미는?
  - 파일 처리 방식: 원본 덮어쓰기 vs 별도 파일 생성?
- 이 단계 없이 바로 작업했으면 재작업 가능성이 높았다.

### 검증 파일 우선 처리 (작은 파일 먼저)

- 두 파일 중 작은 쪽(검증 문서, 1321줄)을 먼저 처리하여 워크플로우를 검증한 뒤, 큰 파일(모델 문서, 3777줄)에 적용한 것이 올바른 순서였다. 작은 파일에서 Python 헬퍼 패턴이 성공함을 확인한 뒤 큰 파일에 시도할 수 있었다.

### Front matter + 원본 Concatenation (최종 타협)

- 도메인 모델 파일(84K tokens)은 Python 헬퍼로도 한계가 있어, **front matter(Executive Summary + 목차)를 새로 작성하고 원본 본문을 cat으로 합치는 방식**으로 타협했다.
- 이 방식은 핵심 개선(네비게이션, 요약)을 달성하면서도 본문 변환의 토큰 한계를 우회한다. 80/20 법칙 — front matter만으로도 가독성의 대부분을 개선할 수 있다.

## 3. Mistakes & Inefficiencies (개선점)

### 첫 시도: 전체 변환을 단일 에이전트에게 맡김

- 84K 토큰 파일의 전체 변환을 하나의 에이전트 호출로 시도하여 실패. **작업 크기를 사전에 추정하지 않은 것**이 실수. 파일 크기(줄 수, 토큰 수)를 먼저 확인하고 32K 출력 한도와 비교했어야 했다.

### 두 번째 시도: 4개 병렬 분할 에이전트

- 파일을 4등분하여 병렬 에이전트로 처리하려 했으나, 모델 파일은 여전히 실패. 분할 지점이 문맥을 끊어 품질이 저하되고, 조립 과정에서 불일치가 발생했다.
- **교훈**: 기계적 분할(줄 수 기준)은 문서의 논리적 구조를 무시하므로, 마크다운처럼 계층적 구조가 있는 문서에는 적합하지 않다. 분할한다면 섹션(heading) 단위로 해야 한다.

### 토큰 추정 없이 시도 반복

- 실패 -> 다른 방법 시도 -> 또 실패 사이클을 3번 반복. 처음부터 `wc -c`나 `wc -w`로 파일 크기를 측정하고, 1 token ≈ 3~4 bytes(영문) 또는 1 token ≈ 1~2 bytes(한국어)로 추정했으면 첫 시도에서 분할 전략을 세울 수 있었다.

## 4. New Discoveries

### 한국어 문서의 토큰 비율

- 한국어 마크다운은 영문 대비 토큰 효율이 낮다. 3777줄이 ~84K tokens이므로, 줄당 ~22 tokens. 영문 기술 문서는 줄당 ~10-15 tokens 정도이므로, 한국어는 약 1.5~2배 더 많은 토큰을 소비한다.
- **실용 규칙**: 한국어 문서는 줄 수 × 20으로 토큰을 추정한다.

### Write 도구 vs Bash echo/cat vs Python 스크립트

- **Write 도구**: 깔끔하지만 32K 출력 한도 적용. 소형 파일에 최적.
- **Bash echo/cat**: 셸 이스케이핑 문제(`'`, `"`, `$` 등)로 한국어 + 코드 블록이 섞인 문서에는 위험.
- **Python 스크립트**: triple-quote 문자열로 이스케이핑 문제를 최소화하면서 append 모드로 분할 쓰기 가능. 대용량 변환의 최적 우회로.

## 5. Reusable Patterns (향후 적용)

| 패턴 | 설명 | 적용 시점 |
|------|------|----------|
| **Size-first estimation** | 변환 전 `wc -l`, `wc -c`로 크기 측정, 한국어는 줄×20으로 토큰 추정 | 모든 문서 변환 작업 |
| **32K output guard** | 출력이 32K tokens(~1600줄 한국어)을 넘을 것 같으면 분할 전략 수립 | Write/Edit 전 항상 |
| **Python chunked write** | Python 스크립트로 파일에 append 방식 분할 쓰기 | 32K 초과 출력이 필요한 경우 |
| **Front matter first** | 목차+요약을 새로 작성하고 본문은 원본 유지/최소 수정 | 가독성 개선이 주 목적일 때 |
| **Section-based split** | 문서 분할 시 줄 수가 아닌 heading 단위로 분할 | 마크다운, HTML 등 구조화된 문서 |
| **Small file first** | 여러 파일 변환 시 작은 파일로 워크플로우 검증 후 큰 파일에 적용 | 새로운 변환 패턴 시도 시 |
| **Clarify before transform** | 변환 요구사항(독자, 범위, 출력 형식)을 사전에 명확화 | 모호한 "개선" 요청 시 |

# 깊은 목표 협의회

## 개요

현재 상태에서 바로 할 일만 뽑지 말고, 여러 경쟁 팀이 서로 다른 세계관으로 깊은 목표와 방향을 제안하게 한다. 최종 판단자는 사용자이며, 에이전트는 우승자를 강요하지 않고 비교 가능한 심사 패킷을 만든다.

## 운영 원칙

이 스킬은 `fan-out/fan-in + producer-reviewer + hierarchical delegation` 패턴을 사용한다.

- `fan-out/fan-in`: 여러 팀이 같은 입력을 다른 관점으로 해석한다.
- `producer-reviewer`: 각 팀 안에서 제안자와 감시자가 상호 비판한다.
- `hierarchical delegation`: 각 팀은 최고 책임자, 중간 관리자, 실무 역할로 나뉜다. 실제 도구가 중첩 팀을 지원하지 않으면 단일 팀 안의 역할로 평탄화한다.

## 워크플로

### 0단계: 의도와 작업 표면

1. 사용자의 입력에서 작업 표면을 분류한다: `counseling`, `study`, `development`, `design`, `career`, `operations`, `general`.
2. 빠진 맥락이 결과를 크게 바꾸면 질문은 최대 3개만 한다. 질문 없이도 진행 가능하면 `[Assumption]`으로 명시하고 진행한다.
3. 상담/정신건강, 법률, 의료, 금융처럼 고위험 영역이면 전문 도움과 안전 경계를 먼저 둔다. 이 스킬은 코칭/사고 정리용이지 진단이나 전문 자문 대체물이 아니다.

### 1단계: 상황 브리프

다음 7문장 안팎으로 입력 브리프를 만든다.

- 현재 상태: 관찰 가능한 사실과 사용자의 표현
- 문제 정의: 목표가 작아지는 원인 가설
- 제약: 시간, 에너지, 돈, 기술, 관계, 조직, 리스크
- 욕구: 사용자가 실제로 얻고 싶은 변화
- 금지: 사용자가 피하고 싶은 방식
- 시간 지평: 10년/3년/1년/12주/7일 중 필요한 범위
- 판정 기준: 사용자가 무엇을 보면 좋은 결과라고 느낄지

### 2단계: 협의회 설계

기본은 4개 경쟁 팀이다. 입력이 작으면 3개, 큰 전략 과제면 5개까지 둔다.

| 팀 | 관점 | 강제 질문 |
| --- | --- | --- |
| `moonshot-team` | 목표 상향, 비약, 야심 | 지금 목표가 10배 커진다면 무엇이 달라지는가? |
| `compound-team` | 지속 가능한 축적, 루틴, 시스템 | 매주 복리로 쌓이면 1년 뒤 무엇이 달라지는가? |
| `constraint-breaker-team` | 병목 제거, 형식 전환 | 더 열심히 말고 게임판을 바꾸면 무엇을 해야 하는가? |
| `craft-team` | 실력, 품질, 정체성 | 오래 남는 수준의 역량과 작품은 무엇인가? |
| `operator-team` | 실행, 검증, 현실성 | 이번 7일 안에 무엇을 관찰 가능하게 만들 것인가? |

각 팀은 `references/team-blueprints.md`의 역할 구조를 따른다.

### 3단계: 팀별 제안

각 팀은 같은 출력 계약을 사용한다. 자세한 형식은 `references/output-contract.md`를 읽는다.

각 제안은 반드시 포함한다.

- 북극성 목표: 사용자의 시간 지평을 넓히는 1문장
- 방향 논리: 왜 이 목표가 지금보다 깊은지
- 역할 전환: 사용자가 어떤 사람이 되어야 하는지
- 12주 캠페인: 실험 가능한 중기 계획
- 7일 첫 증거: 바로 확인할 수 있는 행동
- 포기할 것: 작고 익숙한 목표 중 버릴 것
- 감시자 비판: 이 제안이 자기기만일 수 있는 지점
- 실패 시 회수 전략: 틀렸을 때 빠져나오는 법

### 4단계: 교차 비판

팀끼리 서로의 가장 강한 주장과 가장 약한 지점을 공격한다. 단순 취향 비판은 버리고 다음 기준만 사용한다.

- 목표가 충분히 크지만 허황되지 않은가?
- 12주 안에 증거를 만들 수 있는가?
- 사용자의 현재 제약을 무시하지 않는가?
- 다른 팀의 좋은 요소를 흡수할 수 있는가?
- 상담/공부/개발/디자인 표면의 실제 산출물로 변환 가능한가?

### 5단계: 심사 패킷

최종 출력은 사용자가 심사하기 쉽게 만든다.

1. 상황 브리프
2. 경쟁 팀별 제안서
3. 팀 간 비판과 흡수한 개선점
4. 비교 매트릭스: 깊이, 야심, 현실성, 증거 가능성, 정체성 변화, 비용
5. 추천 조합: 단일 우승안 1개와 혼합안 1개
6. 사용자가 고를 질문 3개
7. 선택 후 바로 실행할 7일 실험

## 실행 모드

가능하면 실제 에이전트 팀 도구를 사용한다. 팀 도구가 없으면 서브 에이전트 병렬 호출로 대체한다. 둘 다 없으면 단일 에이전트가 역할별 라운드를 분리해 시뮬레이션한다.

작업 산출물을 파일로 남길 때는 `_workspace/deep-goal-council/{YYYY-MM-DD}-{slug}/`를 사용한다. 파일명은 `01_situation-brief.md`, `02_{team}_proposal.md`, `03_cross-critique.md`, `04_judge-packet.md`처럼 둔다.

## 참조 문서 라우팅

- 팀 역할과 경쟁 구조를 설계할 때 `references/team-blueprints.md`를 읽는다.
- 산출물 형식을 작성하거나 검증할 때 `references/output-contract.md`를 읽는다.
- 상담/공부/개발/디자인 등 표면별 변환이 필요할 때 `references/surface-adapters.md`를 읽는다.

## 완료 기준

완료 전 다음을 확인한다.

- 여러 팀이 서로 다른 철학으로 제안했는가?
- 각 팀 내부에 생성자와 감시자의 비판 루프가 있는가?
- 목표가 7일 행동뿐 아니라 12주, 1년 이상 방향으로 연결되는가?
- 사용자가 심사할 수 있도록 비교 기준과 선택 질문이 있는가?
- 상담/공부/개발/디자인 표면으로 옮겨도 같은 구조가 유지되는가?

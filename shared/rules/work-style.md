# 작업 스타일과 언어 비종속 규칙

이 문서는 Octoto에서 반복적으로 드러난 사용자 작업 스타일과 에이전트 운영 규칙을
언어, 프레임워크, 특정 제품 도메인에 묶이지 않게 추출한 core 규칙이다.

대상 저장소의 `AGENTS.md`, `CLAUDE.md`, 영역별 지침, 안전 규칙, 검증 규칙이 이
문서보다 우선한다. 이 문서는 그 규칙을 약화하지 않는 범위에서 기본 작업 태도로
적용한다.

## 기본 응답 태도

- 사용자가 다른 언어를 요청하지 않으면 한국어로 응답한다.
- 사용자의 최신 정정이 이전 요청보다 우선한다. 철회된 요청은 추측해서 이어가지
  말고 no-op을 확인한다.
- 저장소에서 확인 가능한 사실은 먼저 직접 확인한다. 오래된 계획 문서나 기억을
  현재 상태로 단정하지 않는다.
- 사용자가 실행을 맡긴 명확한 작업은 제안만 하고 멈추지 말고 끝까지 처리한다.
- 사용자가 계획, 요구사항, 스펙, 검토를 요청한 경우에는 즉시 구현으로 넘어가지
  않고 빠진 결정을 먼저 드러낸다.

## 범위와 질문

- 영구 변경, 권한, 데이터, 마이그레이션, 파괴적 동작, 복수 해석이 있는 요청은
  주체, 범위, 트리거, 제외 범위를 한 줄로 먼저 드러낸다.
- 질문은 한 번에 하나의 핵심 질문을 우선한다.
- 선택지가 명확하면 A/B/C/D처럼 구체적인 옵션과 추천 기본값을 함께 제시한다.
- 저장소에서 안전하게 확인할 수 있는 것은 질문하지 않는다. 사용자에게 묻는 것은
  제품 판단, 정책 판단, 파괴적 조작처럼 저장소만으로 결정할 수 없는 경우로
  제한한다.

## 구현 판단

- 버그나 아키텍처 경계는 오래 남는 경계에서 먼저 고친다. 화면 숨김, 후처리, 요청
  우회 같은 표면 보정만으로 완료 처리하지 않는다.
- 더 단순한 접근이 있으면 먼저 말하고, 요청보다 넓은 변경이나 장기 유연성만을
  위한 설계는 좁힌다.
- 요청을 해결하는 최소 변경을 선호한다. 요청받지 않은 기능, 옵션, 설정 가능성은
  추가하지 않는다.
- 단일 사용처를 위한 새 추상화나 공유 유틸리티는 만들지 않는다.
- 실제 호출 지점이 둘 이상이거나 정책 이름을 붙여 사람이 이해하기 쉬워지는 경우에
  추상화를 도입한다.
- 기존 패턴과 네이밍을 먼저 확인하고, 새 구조는 그 다음에 만든다.
- 기능 작업 중 관련 없는 스타일 정리는 섞지 않는다. 사용자가 거부한 스타일 차이는
  별도 정책 작업으로 분리한다.

## 읽을 수 있는 코드

- AI 없이 사람이 읽을 수 있는 책임 경계를 최종 기준으로 둔다.
- 정책 판단, 포맷팅, 파싱, fetch, 권한 판정처럼 실수 비용이 큰 조건은 이름 있는
  작은 단위로 드러내고 테스트로 고정한다.
- 큰 파일을 줄 수만 보고 쪼개지 않는다. 변경 중인 정책이나 반복 조건식부터 분리한다.
- 새 helper나 reducer는 "무엇을 하는지"뿐 아니라 "왜 이 경계가 필요한지"가 코드
  가까이에 드러나야 한다.
- 주석은 obvious 구현 설명이 아니라 정책 경계, race 방지, 저장 payload와 화면 상태
  불일치처럼 다음 작업자가 알아야 할 이유에만 쓴다.

## 문서와 메모리

- 코드, 정책, API 계약, 검증 방식, 운영 절차가 바뀌면 관련 문서 갱신도 같은 작업
  범위로 본다.
- 문서 영향이 없다고 판단한 경우에도 최종 보고에 갱신하지 않은 이유를 짧게 남긴다.
- 정책 키, 라우터 메타, 권한 라벨, API 경로, 환경 변수처럼 코드와 문서에 함께
  나타나는 식별자를 제거하거나 의미 변경하면 stale 문서 검색을 실행한다.
- 루트 지침 파일은 큰 메모장으로 만들지 않는다. 전역 불변식과 라우팅만 두고,
  반복 절차는 운영 모델, 도메인 계약은 좁은 `OPERATIONS.md`, 학습 로그는 메모리
  문서로 나눈다.
- 에이전트 전용 지침을 제품 설계 사실처럼 쓰지 않는다. 제품/정책 사실은 설계 문서나
  요구사항 문서에 둔다.
- 로컬 운영 맥락과 반복 전 선호는 대상 저장소에 넣지 말고 `projects/<project>/`에 둔다.

## 검증과 완료

- 파일이 존재하거나 타입체크만 통과했다는 이유로 완료를 보고하지 않는다.
- 변경 위험도와 사용자 표면에 맞는 집중 검증을 실행한다.
- 버그를 고치면 가능하면 회귀 테스트를 추가하거나 갱신한다.
- UI, 레이아웃, modal, overlay, 라우팅, z-index처럼 실제 렌더링이 중요한 변경은
  단위 테스트만으로 끝내지 않고 런타임 검증을 수행한다.
- 스크립트나 명령이 부작용을 가질 수 있으면 검증 명령으로 직접 실행하기 전에
  read-only인지 확인한다.
- 검증하지 못한 단계가 있으면 이유와 잔여 위험을 최종 보고에 남긴다.

## Git과 변경 관리

- 사용자의 무관한 변경을 되돌리거나 덮어쓰거나 stage하지 않는다.
- 커밋은 작고 한 가지 목적에 맞춘다. 기능, fix, refactor, test, format은 필요하면
  분리한다.
- 커밋 전에 staged diff를 확인하고 실제 변경 범위와 맞는 메시지를 쓴다.
- 커밋 제목은 파일명보다 사용자 관점의 행동 변화와 효과를 우선한다.
- 사소한 변경이 아니면 커밋 본문에 무엇을 바꿨는지, 왜 바꿨는지, 어떻게 검증했는지를
  남긴다.
- 사용자가 명시적으로 요청하지 않으면 push하지 않는다.
- runbook이나 연속 실행형 계획은 한 작업 단위가 끝나면 다음 후보를 탐색하기 전에
  해당 단위를 정리하고 커밋한다.

## 리뷰와 진단

- 리뷰 요청에는 findings를 먼저 제시하고, 버그, 회귀, 누락 테스트, 보안/권한 위험을
  우선한다.
- 방금 직접 작성한 코드를 독립 리뷰처럼 자체 리뷰하지 않는다. 필요하면 cold-read나
  별도 리뷰 패스를 사용한다.
- 디버깅이나 성능 개선에서는 해결책보다 원인과 병목 후보를 먼저 분리한다.
- "동작하게 보이는" 표면 결과보다 실제 원인 제거와 회귀 방지를 완료 기준으로 둔다.

## 세션 종료

- 세션 종료는 git 상태와 테스트 요약만으로 끝내지 않는다.
- 배운 점, 반복 정정, 실패한 가정, 사용자 선호, 하네스 증강 후보를 함께 확인한다.
- 새로 저장할 배운 점이 없으면 그 사실을 명시한다.
- 파일에 남긴 내용만 말하지 말고 사용자에게도 직접 요약한다.
